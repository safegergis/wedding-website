## Project

A wedding website for guests, built on Nuxt 4. It needs:

- Password-gated access, but reachable without a password via a direct QR code link (i.e. the QR link must bypass/embed the auth check).
- Sections: **Our Story**, **The Details** (the venues, their hours, and the particulars), **Schedule** (the day in order), **Q&A**, **Travel** (getting there), **RSVP**, **Photo Gallery**. There is deliberately **no hotel block**: the couple did not reserve one, so the Travel chapter carries no lodging copy.
- Visual theme: literary/books aesthetic, monochromatic red colorscheme spanning dusty pink to burgundy.

**Mobile first.** Guests will overwhelmingly be on phones. The single leaf is the primary layout; the two-page spread at `>=64em` is the enhancement.

The design pass is done; see Design below. What remains is **the rest of the real content**: the reply-by date and parking. Anything still unknown is bracketed `[Placeholder: ...]`, and the unfilled photographs are hatched `[Photograph]` slots. Keep the bracket convention for anything unfilled so nothing ships by accident.

**No em dashes anywhere**, in guest-facing copy or in source comments. The couple asked for this explicitly. Use a comma, colon, semicolon, or a second sentence instead.

## Commands

Package manager is **pnpm** (see `pnpm-lock.yaml`).

```bash
pnpm install       # install dependencies
pnpm dev           # start dev server at http://localhost:3000
pnpm build         # production build
pnpm generate      # static site generation
pnpm preview       # preview a production build locally
```

There is no lint or test tooling configured yet.

## Deployment

The site is static, generated by `pnpm generate` and published to **GitHub Pages** at the custom domain
`https://msfor.life/` by `.github/workflows/deploy.yml` on every push to `main`. The old
`https://safegergis.github.io/wedding-website/` address now 301-redirects there.

- Nitro runs the `github_pages` preset (set in `nuxt.config.ts`), which writes `.nojekyll` (without it, GitHub would hide the `_nuxt/` directory) and a `404.html` SPA fallback into `.output/public`.
- The custom domain serves from the domain root, so the workflow sets **no** `NUXT_APP_BASE_URL`; everything builds and deploys at `/`, same as local `pnpm dev` and `pnpm generate`. (When the site lived under the project path, the workflow had to bake in `NUXT_APP_BASE_URL=/wedding-website/`; that is exactly what breaks on a custom domain, since every asset URL then 404s and the page renders as bare HTML.)
- `public/CNAME` holds `msfor.life`, matching the domain configured in the repo's Pages settings.
- **The QR link**: `https://msfor.life/?invite=<token>`.
- The gate password and invite token come from the repository variables `WEDDING_PASSWORD` and `INVITE_TOKEN` if set, and fall back to the `nuxt.config.ts` fillers otherwise. Set them with `gh variable set WEDDING_PASSWORD --body '...'`, then re-run the workflow. They are still readable in the client bundle; see the password-gate note above.

## Architecture

- **Nuxt 4** with the default `app/` source directory layout. There is no `pages/` directory: this is deliberately a single-route SPA (`app/app.vue`), not file-based routing. Sections are Vue components swapped via state, not navigated via URL. This was a deliberate choice to make the "page flip" transition work: a single stable DOM tree makes it far easier to keep a `perspective`-wrapped container and animate `rotateY` on the entering/leaving section, versus fighting Nuxt's route-transition/scroll-restoration/SSR-hydration timing across real page navigations.
- **Tailwind CSS v4** is wired in via the `@tailwindcss/vite` plugin in `nuxt.config.ts` (no `tailwind.config.js`). Theme tokens (the monochromatic red scale `--color-blush-50` through `--color-blush-950`, `--color-ink`, and the three font stacks) live in `app/assets/css/main.css` under `@theme`. All hand-written CSS below the theme sits in `@layer components` **on purpose**: unlayered CSS outranks Tailwind's layered utilities, so dropping the layer would silently break every utility class used in the templates.
- **Sections & the book UI**: `app/composables/useBook.ts` holds the ordered list of sections (`cover`, `story`, `details`, `schedule`, `qa`, `travel`, `rsvp`, `gallery`) as module-level singleton state (no Pinia; the app is small enough that a shared `ref` is sufficient), plus the turn `direction`, roman chapter numerals, and folio numbers. `app/components/BookShell.vue` maps the active section id to its component, wraps it in a direction-aware `<Transition :name="`turn-${direction}`">`, and owns the swipe/arrow-key handling. `app/components/BookSpread.vue` is the shared leaf layout every section renders into: a `plate` slot (verso) and the default slot (recto). `app/components/SectionNav.vue` is the contents strip. Section content components live in `app/components/sections/*Section.vue` and are explicitly imported (not relied on via component auto-import) so `BookShell`'s `componentMap` stays predictable.
- **Two footguns in the page turn**, both already hit once:
  - A section component must have **exactly one root node**. A stray HTML comment above the root element makes it a fragment, and `<Transition>` then skips the leave transition silently. No warning, the turn just stops happening. Put template comments *outside* `<template>`.
  - `<Transition>` carries an explicit `:duration`. The turn animation lives on the leaf's children, not on the transitioning `.spread` element, so Vue's automatic duration sniffing finds nothing and ends the transition on the next frame. If you retime the animation in CSS, update `:duration` to match.
- **Password gate**: client-side only, via `app/composables/useAuth.ts`. A cookie (`wedding-auth`) gates access; `app/app.vue` renders `<PasswordGate>` or `<BookShell>` based on it. The password and the QR-code invite token both come from `runtimeConfig.public` in `nuxt.config.ts` (currently filler values `ourstory2026` / `qr-invite`; override via `NUXT_PUBLIC_WEDDING_PASSWORD` / `NUXT_PUBLIC_INVITE_TOKEN` before this goes out to real guests). Because these are `runtimeConfig.public` values, they're readable in the client bundle. That is acceptable for a low-stakes gate, but don't mistake this for real access control. The QR link format is `/?invite=<token>`; `app.vue` checks `route.query.invite` on load and unlocks the cookie if it matches.
- **RSVP is outsourced to Zola.** `RsvpSection.vue` and the RSVP button on `CoverSection.vue` are just links (`target="_blank"`) to `RSVP_URL`, exported from `app/utils/rsvp.ts`. There is no in-site RSVP form or backend.
- **Fonts** are self-hosted at build time by `@nuxt/fonts` (no runtime request to Google). See Design below for which face stands in for which.

## Design

The site is the printed invitation's companion volume: an actual bound book, not a card with a flip effect.

- **The signature is the page-edge stack.** `.book-edge--left` / `--right` flank the leaf, drawing one hairline per leaf from `--leaves-read` / `--leaves-left` (set as inline CSS vars in `BookShell.vue`). The book visibly thickens on the left and thins on the right as you read, so its physical thickness encodes where you are. Everything else stays quiet; this is the one place boldness is spent.
- **Art Deco ornament, in the register of a 1920s–30s fine press book.** The era set old-style faces like Garamond inside geometric Deco devices, which is what keeps this period-consistent rather than a mashup. Three primitives, and nothing outside them:
  - **Stepped forms.** `DecoRule.vue` is the house printer's ornament (stepped pyramid with an apex diamond); `DecoPediment.vue` is the same motif at full scale, used on the title page only, where its stepped crown crowns the couple's names.
  - **Graduated parallel rules.** The fans flanking the ornament, and the rules trailing off every chapter label (`.chapter-mark::after`).
  - **Cut corners.** `.deco-cut` on every action, and `.deco-plate` for the blind-stamped frame on the closed cover. The clip lives on a pseudo-element, never the element: `clip-path` on the button itself would clip the focus ring along with the shape.

  Use `<DecoRule plain />` on a page that already carries the full device, so no page shows the medallion twice.
- **Book vocabulary is structural, not decorative.** Roman chapter numerals, folio page numbers in the outside corners, run-in small-caps side heads, a frontispiece facing the title page, and numbered `Plate I…V` captions in the gallery. The content genuinely is a sequence (the turn is sequential), which is what earns the numbering.
- **Typography.** Three roles, each with the licensed print face named first and a web substitute behind it. See `public/fonts/README.md` for the drop-in upgrade path.

  | Role | Invitation face | Substitute shipped | Where it may appear |
  | --- | --- | --- | --- |
  | Body & headings | Garamond | EB Garamond | everywhere |
  | Large beginning character | Foda Display | Marcellus | drop caps and the couple's names, **nowhere else** |
  | Cursive accent | ITC Edwardian Script | Pinyon Script | one or two lines per spread, **nowhere else** |

  The restraint is the point: if the display or script face starts showing up in more places, the design stops working.
- **Colour.** `blush-300`/`400` are tints for hairlines, rules, and ornament. **Never set text in them**; they fall under 3:1 on paper. `blush-500` is the quiet text tone (the small caps, folios, captions) and clears 4.5:1 on both leaf backgrounds. `blush-600` is the one saturated note, reserved for the drop cap and the RSVP action.
- **Motion.** One orchestrated moment: the leaf pivots on the spine and foreshortens away, revealing the next page beneath. On mobile it pivots on the outer edge, since only one leaf is in view. Turning also responds to swipe and to arrow keys. `prefers-reduced-motion` swaps the turn for a cross-fade. The page still changes, it just doesn't turn.
- **Photographs and art** live in `app/assets/img/`, imported by name in each section's `<script setup>` so Vite fingerprints and bundles them. The engagement photographs (`hero.jpg` on the title page, `ourstory.jpg`, `schedule.jpg`) render through `.plate-photo`: a hairline frame, natural proportions, no crop and no caption. The two venue watercolours (`church.webp`, `venue.webp`) render through `.plate-art` on the Details plate, one over each address, paired by `VENUES` order. They are painted on white rather than feathered into transparency, so `.plate-art` uses `mix-blend-mode: multiply` to drop the white into the plate ground; a drop shadow would only outline the white rectangle, which is why they do not use `.vignette`. The files in `app/assets/img/` are resized for the web (long edge ~1100 to 1400px, since nothing displays wider than 20rem); the camera-resolution originals are **not** in the repo (they were 61MB and would be re-downloaded on every CI checkout), so re-export from the couple's own copies if a plate ever needs more. `public/images/venue.png` is the old low-resolution watercolour and is no longer referenced.
- **The gallery** (Chapter VII) prints all 53 engagement photographs: Plate I full on the verso, the rest as a numbered square grid on the recto. The sources live in `public/images/gallery/ms-01.jpg` through `ms-53.jpg` (resized to a 1400px long edge, like every other plate) and are served through `@nuxt/image`: guests only ever fetch the optimized `/_ipx/` webp renditions, which `pnpm generate` writes out as static files. Because the book renders client side behind the gate, no prerendered page ever references those URLs, so `app.vue` resolves every rendition at generate time to register it with nitro. The ipx modifier constants live in `app/utils/gallery.ts` and are shared by that registration and by `GallerySection.vue`; they must stay shared, since the modifier string is baked into each generated file's path and any drift between the two is a 404 in production.
- **Favicon.** A Coptic cross (each arm ending in three points, as the tradition draws it) in the site's palette. `public/favicon.svg` is the source of truth; `favicon.ico`, `favicon-96x96.png`, and `apple-touch-icon.png` beside it are rasterized from it (the apple touch icon with square corners, since iOS rounds them itself), and `nuxt.config.ts` links them in `app.head`.
- **Placeholders to fill in**: the hatched `[Photograph]` slots (`.plate-slot`) on the Q&A and Travel plates, plus every remaining bracketed fact. Both venues live in `app/utils/venues.ts` as `VENUES`, printed by both the Details plate and the Schedule, and the Maps links are derived from the address, so correcting an address there corrects everything downstream.
